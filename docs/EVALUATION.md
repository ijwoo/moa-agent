# 평가

모델 성능은 채팅 품질이 아니라 **실제 작업 완료 능력**으로 측정한다. 측정하지 못한 값은 "미측정"으로 둔다.

## 지표
| 지표 | 정의 | 시작 Phase |
|---|---|---|
| 구조화 출력 유효성 | 스키마 검증을 통과한 응답 비율 | 1 |
| 필드 정확도 | 기대값과 일치한 필드 비율 (의도, 대상, 승인 필요 여부 등) | 1 |
| 지연 | 요청~응답 시간 p50 / p95 | 1 |
| 자원 | 추론 중 메모리(RSS·통합 메모리), CPU/GPU 사용 | 1 |
| 도구 호출 정확도 | 올바른 도구 + 유효한 인자 비율 | 2 |
| 잘못된 도구 선택 | 허용 목록 밖·상황에 맞지 않는 도구 선택 횟수 | 2 |
| 작업 성공률 | 검증 기준을 통과한 작업 비율 | 4 |
| 작업당 LLM 호출 수 / 완료 시간 | 성공 작업 기준 평균 | 4 |
| 실패 후 복구 성공률 | 도구 실패 뒤 다른 방법으로 완료한 비율 | 4 |
| 잘못된 완료 선언 | 완료라고 했지만 검증 실패 | 4 |
| 승인 없이 수행된 민감 작업 | **0이어야 함** | 4 |

## 비교 조건 (Qwen vs Claude)
- 같은 작업, 같은 초기 브라우저 상태, 같은 도구 목록·스키마, 같은 제한(단계·시간)에서 실행한다.
- 모델별 설정(온도, thinking 여부, 최대 토큰)을 결과와 함께 기록한다.
- 테스트 사이트는 로컬에 띄운 합성 사이트를 우선 쓴다 (외부 사이트 변화로 결과가 흔들리지 않게).

## 시나리오 형식 (예정)
```json
{
  "id": "p1-001",
  "input": "지난 회의에서 요청한 자료가 메일로 왔는지 확인해줘",
  "expected": { "intent": "check_email", "needs_approval": false },
  "notes": "합성 데이터"
}
```
Phase 1은 한국어 명령 20개(합성)로 시작한다.

## 실행 로그 규칙
- 기록: 시각, 모델·Provider, 설정, 시나리오 id, 도구 호출(이름·검증 결과·소요 시간), 결과, 실패 사유, 토큰 수.
- **기록 금지**: 비밀번호, 쿠키, 토큰, API 키, 실제 개인 정보·메일 본문. 테스트는 합성 데이터와 테스트 계정만 쓴다.

| ─ intent | 54/60 (90.0%) |
| ─ target | 36/36 (100%) |
| ─ time_ref | 39/42 (92.9%) |

틀린 항목 (3회 모두 같은 결과):
- p1-008, p1-009: `web_extract`를 `web_search`로 분류. "특정 사이트에서 확인" vs "검색"의 의도 정의가 모호 → 프롬프트·의도 설계 문제로 판단.
- p1-001: "지난 회의"를 time_ref로 분리하지 않고 target("지난 회의에서 요청한 자료")에 포함.
- p1-014: 정보가 충분한데 needs_clarification=true. p1-017("그 메일 보내줘"): 대상이 불명확한데 false.

목표치(제안, 다음 측정부터 적용): 유효율 100% 유지, intent ≥ 95%, needs_approval(정책 적용 후) 100%, p95 ≤ 3초.
주의: 평가 세트가 20개뿐이라 프롬프트를 이 세트에 맞춰 고치면 과적합된다. 개선 시 별도 검증 세트를 함께 둔다.

  컨테이너 브라우저와 맥의 Chrome 모두 같았고(창 크기·움직임 줄이기 설정과 무관, 4/4), 참고 앱도 같은 곳에서 "하얗게 멈춰서 새로 열었다"고 했다. 사이트가 막은 것이 아니다.
  브라우저의 읽기 동작 가운데 시간 한도가 없는 것(제목·칸 찾기)은 끝없이 기다렸고, 30초 뒤 서비스가 통째로 닫혔다.

  합성 화면 2종(처음에만 멈춤 / 계속 멈춤)으로 통합 테스트.
- 고친 뒤 그 사이트: 0.6초에 로그인 화면을 읽었다 — 이메일 칸 + 비밀번호 칸 + 로그인 단추(공통 로그인이 알아봄), **이름 없는 단추 2개**(소셜 로그인으로 보임 — 글자가 없어 무엇인지 코드가 모른다).

### 검색 담당 모델의 "저는 할 수 없어요"가 답으로 나갔다 (2026-11-15 16:22, 실기기)
- 사용자가 네이버 결제내역 읽기 뒤에 더 깊은 것(항목마다 상세를 열어 확인)을 바랐다. 판단은 그것을 공개 길(일반 길)로 보냈다(기록: `action=browse` → `steps=3 sites=0 gave_up=True fell_back=True`). 공개 길은 열 수 있는 곳이 없어 포기했고, 검색으로 바꿨고, 검색 담당 모델이 "죄송하지만 저는 이 작업을 할 수 없어요 … 제가 가진 도구는 웹 검색뿐이라"를 썼다. 그것이 "검색 결과로는 이렇게 나와요" 아래에 답으로 나갔다.
- 틀린 것 셋: (1) 내 계정 안의 일을 공개 길로 보냄 (2) 로그인한 화면이어야 하는 일을 검색으로 바꿈 (3) 검색이 쓴 "못 한다"를 답으로 씀.
- 고침: (1) 판단 지시 — 내 주문·결제·리뷰·마이페이지는 공개 길이 아니다. 정해진 읽기보다 깊은 것을 바라면 되는 데까지와 안 되는 것을 솔직히 말한다. (2) 직접 못 한 까닭이 "로그인이 필요해서"면 검색으로 바꾸지 않고 "이 일은 로그인한 화면 안에서만 볼 수 있어서 공개 웹으로는 하지 못했어요 …"라고 답한다. (3) 검색이 쓴 글이 "할 수 없다"는 말이면 쓰지 않는다.
- 앱 세션이 알려 준 것: 답이 검색에서 왔는데도 답 아래에 그 사이트의 화면 캡처와 "열기"가 붙어 그 화면에서 읽은 답처럼 보였다 → 답이 그 사이트에서 온 것이 아니면 캡처를 붙이지 않고 `report.sources`를 비운다.

### 구글 계정으로만 로그인하는 사이트 — 계정을 받고 나서야 막혔다고 했다 (2026-11-15 18:24, 실기기)

- 구글이 받지 않는다는 것은 낮에 이미 알았고(실기기), 그래서 "구글로 로그인" 단추는 고를 방법에서 뺐었다. 그런데 **단추가 아니라 주소가 곧바로 그 회사의 로그인 화면으로 넘어가는 사이트**에는 그 지식을 쓰지 않았다. 사용자는 계정을 입력하고 25초 뒤에야 막혔다는 것을 알았다.

- 합성(`/e/login` — 로그인 주소가 다른 호스트로 넘어간다, 그 호스트를 받지 않는 회사의 것으로 다룸): 입력 칸을 보여 주지 않고 멈춘다. 로그인 통합 34, 단위 385.

- 이것으로 **구글 계정으로만 로그인하는 서비스(유튜브·지메일 등)는 이 방식으로는 로그인할 수 없다**는 것이 정해진 사실이다. 우회하지 않는다.
