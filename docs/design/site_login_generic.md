# 사이트에 상관없는 공통 로그인 — 설계 (D53의 다음 과제)

상태: **설계 초안, 구현 전**(2026-11-12). 구현은 사용자 확인 뒤에 한다. 앱이 바꿀 것은 6절. 앱 세션의 검토(같은 날)를 반영했다 — 11절.

## 1. 목표와 범위
- 목표: 미리 준비하지 않은 사이트도 **사용자가 앱에서 직접 로그인**해 두면, 에이전트 브라우저가 그 로그인 상태로 일한다(D53: 로그인해 주는 행위가 동의, 로그아웃이 철회).
- 지킬 것(그대로): 아이디·비밀번호는 저장하지 않고 기록·모델 입력·캡처에 넣지 않는다. 캡차·2단계 인증은 우회하지 않는다. 자동화 표시를 숨기지 않는다.
  남는 것은 로그인된 상태(쿠키)뿐이고 맥의 키체인에만 둔다.
- 하지 않는 것: 공동인증서·보안 프로그램 설치·가상 키패드처럼 일반 브라우저 화면 밖의 수단이 필요한 로그인(은행·정부 사이트 다수). 사이트가 자동 브라우저를 막으면 `blocked`로 끝낸다(돌아가지 않는다).

## 2. 지금 구현이 네이버에 묶여 있는 곳 (`src/agent/sites/login.py`)
| 무엇 | 지금 | 왜 다른 사이트에서 안 되나 |
|---|---|---|
| 입력 칸 알아보기 | 칸 이름에 "아이디"·"비밀번호"·"정답" 같은 한국어 낱말이 있는지 | 사이트마다 이름이 다르다("이메일", "Username", "휴대폰 번호") |
| 틀림·승인 대기·막힘 알아보기 | 네이버 화면 문구 목록(`WRONG`·`APPROVAL`·`BLOCKED`) | 문구가 다르다 |
| 로그인됐는지 | 쿠키 이름 `NID_AUT`·`NID_SES` | 사이트마다 다르고 미리 알 수 없다 |
| 로그인 주소·확인 주소 | 코드에 적어 둠 | 모르는 사이트는 적어 둘 수 없다 |
| 앱의 입력 칸 | `id`·`password`·`captcha`·`code`만 그린다 | 칸 종류가 더 있다(이메일, 전화번호, 생년월일…) |

## 3. 방식 비교
| | (가) 사이트별 규칙 | (나) 화면 뼈대 중계(공통 양식) | (다) 화면 그대로 중계 |
|---|---|---|---|
| 방법 | 사이트마다 문구·쿠키를 적어 둔다(지금 네이버) | 서버 코드가 **HTML 표준 속성**으로 칸을 가려 앱에 양식으로 넘긴다 | 브라우저 화면 그림을 앱에 보내고, 사용자의 터치·글자를 브라우저로 옮긴다 |
| 모르는 사이트 | 안 됨 | 표준 양식이면 됨 | 거의 다 됨(그림 캡차·끌기 포함) |
| 앱 화면 | 지금 그대로 | 지금 카드 + 칸 이름을 서버가 준 대로 | 새 화면(그림 위 터치, 글자 입력 중계) — 큰 작업 |
| 약점 | 사이트 수만큼 만든다 | 표준에서 벗어난 화면에서 멈춘다 | 작은 폰 화면에서 PC 페이지를 다루기 불편, 지연 |

**추천: (나)를 기본으로, 막히면 (다)로 넘어가고, 네이버처럼 이미 만든 (가)는 그대로 둔다.**
(다)만으로도 목표는 채워지지만 매번 그림을 눌러 로그인하는 것은 불편하다. (나)가 되는 사이트가 얼마나 되는지는 **재 봐야 안다**(9절).

## 4. (나) 공통 양식 — 서버가 화면을 가리는 법
로그인 단계는 지금처럼 **모델이 아니라 서버 코드**가 진행한다. 낱말 대신 브라우저가 알려 주는 표준 속성을 쓴다.
- 칸 종류(`kind`): `type=password` → `password`(가림) / `autocomplete=one-time-code` 또는 숫자 전용·길이 4~8 → `code` /
  `type=email|tel|text` → `text` / 그림과 같이 있는 글자 칸 → `captcha`. 체크 상자("로그인 상태 유지")는 건드리지 않는다.
- 칸 이름은 뜻 없는 번호(`f1`, `f2`…)로 주고, 사용자에게 보일 글은 화면의 칸 이름·안내 글(`label`) 그대로다.
- 제출 단추: 양식의 제출 단추(없으면 마지막 칸 다음의 단추).
- 화면이 바뀐 뒤: 칸이 있으면 다시 `need_input`. **같은 칸이 그대로 다시 나오면 틀린 입력으로 센다**(문구를 몰라도 됨 — 지금도 쓰는 규칙). 3번이면 끝낸다(계정 잠김 방지).
- 칸이 없고 무엇을 해야 할지 코드가 모르는 화면(승인 대기, 번호 고르기, 안내): **화면 그림을 그대로 보여 주고** 사용자에게 고르게 한다(`need_confirm`, 5절).
- 로그인됐는지: 모르는 사이트는 쿠키 이름을 모른다 → **사용자가 화면을 보고 "로그인됐어요"를 누른다**. 그때 쿠키를 보관하고, 그 화면의 주소를 '확인 주소'로 적어 둔다.
  나중에 확인할 때는 확인 주소를 열어 비밀번호 칸이 나오거나 다른 호스트로 넘어가면 풀린 것으로 본다.

## 5. API (X-Api-Version 5, `health.features`에 `"site_login_generic"`) — 지금 형식에 더하는 것
기존 주소(`/v1/sites/...`)와 `L` 객체는 그대로다. 버전 4 앱에는 지금처럼 네이버만 보인다.

- 시작: `POST /v1/sites/login {"url": "https://example.com"}`(주소) 또는 기존 `POST /v1/sites/{site}/login`.
  사이트 키는 경로에 넣는 값이라 **영문 소문자·숫자·`_`·`-`만** 쓴다(도메인의 점은 `-`로: `example-com`). 화면에 보일 도메인은 `name`·`page.host`로 따로 준다.
  **https가 아닌 주소는 시작하지 않는다**(400 `not_https`).
  주소는 **사용자가 준 것만** 쓴다(모델이 주소를 짐작하지 않는다). 자주 쓰는 사이트는 서버의 이름→주소 표로 찾고, 표에 없으면 대화 담당이 주소를 묻는다.
- `L`에 더해지는 값:
  | 값 | 뜻 |
  |---|---|
  | `page: {"host", "https": true}` | 지금 입력을 받는 화면의 호스트. **앱은 입력 칸 위에 항상 보여 준다**(엉뚱한 곳에 비밀번호를 넣지 않게). `https`는 항상 `true`다(아닌 화면이 나오면 서버가 `failed`/`not_https`로 끝낸다). 앱도 `false`면 입력받지 않는다 |
  | `fields[].kind` | `text` \| `password` \| `code` \| `captcha`. `name`은 `f1`…(뜻 없음) — 앱은 이름이 아니라 `kind`로 그린다. `secret == true`이거나 `kind == "password"`면 가림 입력(둘은 항상 같이 온다). `code`는 숫자만인 인증번호(숫자 자판) — 영문이 섞인 코드는 `text`로 준다. **한 화면에 칸은 4개까지, `label`은 40자까지, 로그인 양식 안의 칸만** 준다(넘으면 서버가 `unsupported_login`으로 끝낸다) |
  | `actions: [{"id", "label"}]` | 지금 화면에서 누를 수 있는 보조 동작. 처음에는 `refresh_captcha`("그림 새로 받기")뿐. 목록에 있는 것만 단추로 그린다 |
  | `screen: {"mime": "image/jpeg", "b64", "width", "height"}` | 화면 그림(가로 최대 1080, 300KB 이하). `need_confirm`·`need_approval`에서 온다 |
  | `number` | 2단계 인증에서 화면이 보여 주는 번호(찾았을 때만). **문자열**(앞자리 0 유지), 8자 이하. 못 찾으면 `screen`으로 본다 |
- 새 상태:
  | state | 오는 것 | 앱이 할 일 |
  |---|---|---|
  | `need_confirm` | `message`, `screen`, `choices`(예: "로그인됐어요", "아직이에요", "그만하기") | 그림과 선택 단추. `{"values": {"choice": …}}`로 보낸다 |
  | `need_host_ok` | `message`("accounts.example.net으로 넘어갔어요. 계속할까요?"), `page`, `choices`(`["계속", "그만하기"]`) | 호스트가 처음 것과 달라졌을 때 한 번 묻는다. `need_confirm`과 같은 꼴로 `{"values": {"choice": …}}`. "그만하기"면 `failed`/`host_refused`. (`/cancel`을 불러도 된다 — 그때는 `cancelled`) |
  | `need_screen` (2단계, 방식 다) | `screen`, `inputs: ["tap", "text", "key"]` | 그림 위 터치 좌표·글자를 `…/input {"step", "event": {…}}`로 보낸다 — 형식은 2단계에서 정한다 |
- 보조 동작 제출: `POST …/input {"step": n, "action": "refresh_captcha"}` → 새 그림과 함께 `step`이 는다. 한 로그인에 5번까지(넘으면 409 `too_many_refresh`).
  서버는 화면에 원래 있는 "새로고침" 단추를 누를 뿐이다(우회 아님).
- `choices`는 지금 `need_choice`처럼 **문자열 배열**이고, 고른 글을 그대로 `values.choice`로 돌려보낸다(객체로 바꾸지 않는다).
- `actions`는 앱이 아는 `id`만 단추로 그린다(지금은 `refresh_captcha`). 새 `id`는 앱이 바뀐 뒤에 보인다.
- 새 실패 사유: `unsupported_login`(인증서·보안 프로그램·키패드, 칸이 4개를 넘는 양식 등), `host_refused`(사용자가 넘어간 호스트를 거절), `not_https`.
- `health.features` 이름(확정): `site_login_generic`, 보고의 캡처는 `report_attachments`.

### 만료(로그인 풀림)를 앱에 알리는 법
서버가 먼저 돌아다니며 확인하지는 않는다(MVP에서 능동 실행 없음). **쓸 때 확인**한다.
1. 작업·기능이 그 사이트를 열었는데 로그인 화면으로 돌려보내지면: 서버가 그 사이트를 `logged_out`(사유 `expired`)으로 적고, 보관한 죽은 쿠키를 지운다.
   그 작업은 `status: "failed"`, `outcome: "needs_login"`, `reason: "login_expired"`(로그인한 적이 없으면 `login_missing`), `result.action: {"type": "site_login", "site": "naver"}`로 끝난다 — 앱은 "다시 로그인" 단추를 그린다.
   `action`을 모르는 지금 앱에서도 이유가 보이게 `report.blocked` 첫 줄에 "네이버 로그인이 풀렸어요. 다시 로그인해 주세요"가 들어간다. **(구현됨 2026-11-12, `site_read`)**
2. `GET /v1/skills`: 그 사이트가 필요한 카드가 다시 `available: false`가 되고 `needs[]`가 생긴다. **(구현됨 2026-11-12)**
   `needs[].reason`: `"never"`(로그인한 적 없음) \| `"expired"`(풀림). `message`도 달라진다("네이버 로그인이 풀렸어요. 다시 로그인해 주세요").
3. `GET /v1/sites`: `status`, `checked_at`에 더해 `reason`(`expired`일 때). 앱이 직접 확인하고 싶으면 지금처럼 `POST /v1/sites/{site}/check`.
4. 대화에서 그 기능을 부탁했는데 풀려 있으면: 답과 함께 `action: site_login`(지금 로그인 안 돼 있을 때와 같다).

### 2단계 인증 번호
- 승인 대기 화면에 번호가 있으면(번호 맞추기) `number`로 주고 `message`에 넣는다("휴대폰 알림에서 37을 골라 주세요").
- 공통 방식에서는 코드가 번호를 못 찾을 수 있다 → `need_approval`에도 `screen`을 같이 준다. 사용자는 그림에서 직접 본다.
- 문자·인증 앱의 번호를 입력하는 화면은 `need_input`의 `kind: "code"`(숫자 자판, iOS의 인증번호 자동 채움을 쓸 수 있다).

## 6. 앱이 바꿔야 할 것 (요약 — 구현은 사용자 확인 뒤)
1. 입력 칸: 이름(`id`·`password`…)이 아니라 `kind`로 그린다. 모르는 `kind`면 그 로그인은 "앱을 업데이트해야 해요"로 멈춘다(지금 원칙 유지).
   `password`는 가림 입력, `code`는 숫자 자판, `captcha`·`text`는 한글도 되는 기본 자판.
2. 입력 칸 위에 `page.host`를 항상 보여 준다. `need_host_ok`에서 계속/그만.
3. `actions`의 단추(지금은 "그림 새로 받기").
4. `need_confirm`·`need_approval`의 `screen` 그림과 `number` 크게 보이기.
5. 작업 결과 `needs_login`과 카드 `needs[].reason == "expired"`의 글·단추.
6. (2단계) `need_screen` 화면 중계 — 따로 정한다.
- 화면 그림에는 사용자가 넣은 아이디가 보일 수 있다(비밀번호는 브라우저가 가린다). 앱은 그림을 저장·공유·클라우드 경로로 보내지 않는다.

## 7. 보안
- 비밀번호 종류 칸의 값은 지금처럼 브라우저 칸에 넣고 버린다(`secret_type`). 기록·응답·오류·모델 입력에 없다. 화면 그림도 기록하지 않는다(개발용 기록은 꺼 둔다).
- **https가 아닌 화면에서는 입력을 받지 않는다**(`unsupported_login`).
- 엉뚱한 사이트: 주소는 사용자가 준 것만, 호스트를 앱에 항상 표시, 로그인 도중 다른 도메인으로 넘어가면 사용자에게 묻는다(통합 로그인 — 예: 구글 계정으로 로그인 — 은 사용자가 보고 허락).
- 보관: 쿠키는 사용자가 확인한 도메인 것만 키체인에. 사이트마다 따로. `logout`이 지운다.
- 그 사이트에서 에이전트가 할 수 있는 일은 로그인과 별개로 기능 파일·정책(허용 호스트, 읽기 전용, 승인)으로 정한다. 로그인됐다고 아무 일이나 하지 않는다.
- 사이트 이용 약관: 자동 접근을 금지하는 사이트가 있다. 사이트를 더할 때 확인한다(누가 어떻게 확인할지는 10절).

## 8. 구현 순서(안)
1. 브라우저 쪽에 로그인 전용 동작 `form_fields`(보이는 입력 칸의 type·autocomplete·inputmode·maxlength·이름) 추가, 서버에 공통 분류기. 기존 네이버 흐름은 그대로 두고 **합성 로그인 사이트 2~3종**(이메일+비밀번호, 2쪽짜리(아이디 → 비밀번호), 인증번호)으로 테스트.
2. API v5(위 5절) + 만료 알림(`needs_login`, `needs[].reason`). 만료 알림은 네이버에도 바로 쓸 수 있어 먼저 넣을 수 있다.
3. 캡차 새로 받기(`actions`) — 네이버에 먼저.
4. 실제 사이트 1곳 시험(사용자가 고르고 승인) → 되는 것·안 되는 것 기록.
5. (다) 화면 중계 — 3·4에서 막히는 화면이 실제로 얼마나 나오는지 본 뒤.

## 9. 확인 못 한 것 (재야 하는 것)
- 실제 사이트의 로그인 화면이 표준 속성으로 얼마나 가려지는가 — 다른 사이트 접속은 승인 전이라 열어 보지 않았다.
- 사용자가 "로그인됐어요"를 누르는 방식의 확인 주소가 만료를 제대로 가려내는가.
- 화면 그림 크기(가로 1080·300KB)에서 번호·안내 글이 폰에서 읽히는가.
- 네이버 로그인 상태가 며칠 가는가(D52에서 미확인 그대로).

### 9-1. 잰 것 — 실제 로그인 화면의 꼴 (2026-11-15, 사용자 결정 "네이버처럼 내가 입력하는 식으로" 뒤)

- 설계를 고칠 것: ① 칸이 `<form>` 밖에 있는 곳이 3곳 — 제출 단추를 양식으로 찾지 못한다(비밀번호 칸 다음의 단추로). ② 한 화면에 로그인 묶음이 여럿인 곳(회원·비회원, 칸 12개) — **비밀번호 칸과 그 바로 앞의 글자 칸**만 한 묶음으로 본다. ③ 로그인 호스트가 따로인 곳 2곳 — `need_host_ok`가 실제로 필요하다. ④ 처음부터 캡차 표시가 있는 곳 1곳.

- 아직 모르는 것: 제출 **뒤**의 화면(틀림 안내, 기기 확인, 2단계 인증, 캡차)은 실제 계정으로 해 봐야 안다 — 사용자가 직접 하는 단계다. 자동 브라우저의 로그인을 사이트가 받아 주는지도 그때 안다.

### 9-2. 만든 것 (2026-11-15, D70) — 설계와 달라진 곳
- (나) 공통 양식을 맥 쪽에 구현했다: 브라우저 동작 `form_fields`·`form_fill`·`form_submit`·`form_image`, 흐름 `_run_generic`.
- **API v5 없이 지금 형식으로 갔다.** 칸을 뜻 없는 번호(`f1`…)와 `kind`로 주는 대신, 역할 이름 `id`·`password`·`code`·`captcha`로 준다 — 지금 앱이 그리는 이름 그대로라 앱의 보안 조건("정해 둔 이름의 칸만 그린다")을 바꾸지 않아도 된다.
  호스트는 `message`에 넣고(`page` 객체 대신), 호스트가 바뀌면 `need_choice`로 묻고(`need_host_ok` 대신), 끝났는지도 `need_choice`로 묻는다(`need_confirm`+화면 그림 대신 화면 글 300자).
- 그래서 못 하는 것: 아이디·비밀번호·인증번호·캡차가 아닌 칸(생년월일 등), 글이 아니라 그림으로만 알 수 있는 화면(번호 고르기), 캡차 새로 받기. 실제 사이트에서 막히는 것을 본 뒤 v5의 해당 부분을 더한다.
- 9-1에서 고치기로 한 것 반영: 제출 단추를 양식 밖에서도 찾는다, 로그인 묶음은 첫 비밀번호 칸과 그 앞의 글자 칸만, 다른 호스트는 입력 전에 묻는다.

## 10. 사용자가 정할 것
1. 방식: (나) 기본 + (다) 예비로 갈지, 처음부터 (다)만으로 갈지.
2. 첫 실제 시험 사이트(네이버 다음).
3. 금융·결제 사이트를 범위에서 뺄지(추천: 뺀다 — 인증 수단이 브라우저 밖이고 사고의 크기가 다르다).
4. 약관 확인을 누가 하나(추천: 사이트를 더할 때 서버 쪽에서 확인해 기능 파일에 적고, 금지면 올리지 않는다).

## 11. 앱 세션 검토에서 나온 것 (2026-11-12)
- 앱(빌드 30)은 모르는 값을 버리므로 `needs[].reason`, `/v1/sites`의 `reason`, `report.attachments`가 와도 깨지지 않는다. 만료 안내(`message`)는 지금 앱의 카드에도 그대로 보인다.
- **사용자가 정할 것으로 넘어온 것**:
  1. 입력 칸을 `kind`로 그리기 — 지금 앱의 "정해 둔 이름(`id`·`password`·`captcha`·`code`)의 칸만 그린다"는 사용자가 정한 보안 조건이라, 바꾸려면 사용자 결정이 필요하다.
  2. 새 사이트의 주소를 어디서 넣나 — 대화에서 말하면 `action`으로 오게 할지, 앱의 연동 화면에 "사이트 추가"를 둘지.
  3. 캡처를 처음엔 가려 두고 누르면 보이게 할지.
  4. 만료 알림과 "그림 새로 받기" 중 무엇을 먼저 할지(만료 알림은 앱을 바꾸지 않아도 카드에 보인다. 그림 새로 받기는 앱에 단추가 생겨야 쓴다).
